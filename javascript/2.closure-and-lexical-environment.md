# JavaScript: Closure and Lexical Environment

## 1. What is a Closure?

A closure happens when a function retains access to variables from its **lexical environment**, even after the outer function has finished executing.

A useful mental model is:

> **Closure = Function + access to its lexical environment**

Example:

```js
function outer() {
  let x = 10;

  return function inner() {
    console.log(x);
  };
}

const fn = outer();

fn();
```

Output:

```txt
10
```

At first glance, it may seem strange because `outer()` has already finished.

But `inner` still has access to the `x` binding from `outer`.

---

# 2. Closure Does Not Copy the Value

A common misunderstanding is:

> "The inner function copies the value of `x`."

That is not the right mental model.

The function retains access to the **binding**.

Example:

```js
let x = 10;

const fn = () => x;

x = 20;

console.log(fn());
```

Output:

```txt
20
```

The function does not contain a frozen copy of `10`.

It accesses the current binding of `x`.

---

# 3. Closure After the Outer Function Returns

Consider:

```js
function createCounter() {
  let count = 0;

  return function increment() {
    count++;
    return count;
  };
}

const counter = createCounter();

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3
```

`createCounter()` has already finished.

However, the returned function still has access to:

```text
count
```

Conceptually:

```text
createCounter()
      ↓
Lexical Environment
      ↓
count → 0
      ↑
      │
increment() retains access
```

Calling `counter()` changes that same binding:

```text
count → 0
count → 1
count → 2
count → 3
```

---

# 4. Separate Closure = Separate Environment

Consider:

```js
function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const a = createCounter();
const b = createCounter();

console.log(a()); // 1
console.log(a()); // 2
console.log(b()); // 1
console.log(a()); // 3
console.log(b()); // 2
```

Why does `b()` start from `1` instead of `3`?

Because `a` and `b` came from **different executions** of `createCounter()`.

Conceptually:

```text
First createCounter():
Environment A
count → 0
   ↑
   a()

Second createCounter():
Environment B
count → 0
   ↑
   b()
```

Therefore:

```text
a → Environment A
b → Environment B
```

They have separate `count` bindings.

---

# 5. Closure and `var` in Loops

Consider:

```js
var functions = [];

for (var i = 0; i < 3; i++) {
  functions.push(function () {
    return i;
  });
}

console.log(functions[0]());
console.log(functions[1]());
console.log(functions[2]());
```

Output:

```txt
3
3
3
```

Why?

`var` creates one function-scoped binding for `i`.

Conceptually:

```text
One shared binding:

i → 0
i → 1
i → 2
i → 3

function 0 ──┐
function 1 ──┼──→ same i binding
function 2 ──┘
```

After the loop finishes:

```text
i → 3
```

Therefore all functions return `3`.

---

# 6. Closure and `let` in Loops

Now compare:

```js
const functions = [];

for (let i = 0; i < 3; i++) {
  functions.push(function () {
    return i;
  });
}

console.log(functions[0]());
console.log(functions[1]());
console.log(functions[2]());
```

Output:

```txt
0
1
2
```

With `let`, each iteration gets a separate binding.

Conceptually:

```text
Iteration 0:
i₀ → 0
 ↑
function 0

Iteration 1:
i₁ → 1
 ↑
function 1

Iteration 2:
i₂ → 2
 ↑
function 2
```

The important word is:

> **Binding**

It is better to say that each iteration gets a different binding rather than simply saying "a new reference is created."

---

# 7. Closure + Scope Chain

Closure is closely related to lexical scope.

Example:

```js
function outer() {
  let x = "outer";

  function inner() {
    console.log(x);
  }

  return inner;
}

const fn = outer();

fn();
```

When `fn()` runs, the lookup is:

```text
inner scope
    ↓
outer lexical environment
    ↓
x = "outer"
```

The `outer` function has already returned, but the lexical environment containing `x` remains accessible to `inner`.

---

# 8. Closure Does Not Mean the Outer Function Stays on the Call Stack

This is an important distinction.

When this happens:

```js
const fn = outer();
```

`outer()` executes and eventually finishes.

It is incorrect to think:

```text
outer() is still running forever
```

or:

```text
outer() is still on the call stack
```

Instead:

```text
outer()
  ↓
execution finishes
  ↓
returned function still has access
  ↓
closure keeps the required lexical environment reachable
```

The call stack and closure are different concepts.

---

# 9. `return` Is Executed When the Function Is Called

Consider:

```js
function outer() {
  let x = 10;

  return x;
}

console.log(outer());
```

The `return x` does not execute when the function is defined.

It executes when:

```js
outer()
```

is called.

Similarly:

```js
function outer() {
  let x = 10;

  return function () {
    return x;
  };
}
```

The returned inner function is created/returned during the execution of `outer()`.

Later:

```js
const fn = outer();

fn();
```

the inner function executes and reads `x`.

---

# Key Mental Model

When thinking about closures, remember:

```text
Function
   +
Access to lexical environment
   =
Closure
```

The function does not necessarily copy values.

It retains access to bindings from its lexical environment.

---

# Final Closure Flow

```text
createCounter()
      ↓
creates lexical environment
      ↓
count = 0
      ↓
returns inner function
      ↓
outer execution finishes
      ↓
inner function still has access to count
      ↓
counter()
      ↓
reads/modifies count
```

The most important ideas are:

1. Closure is about **access to lexical environments**.
2. Closure accesses **bindings**, not frozen copies of values.
3. Different executions can create **different environments**.
4. `var` in a loop commonly creates one shared binding.
5. `let` in a loop provides separate per-iteration bindings.
6. A closure does not mean the outer function remains on the call stack.
